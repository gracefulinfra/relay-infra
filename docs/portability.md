# Portability

How Relay moves from one Kubernetes environment to another, and the rehearsal that proves the
mechanism (P0-07). The pitch requires portability to be **demonstrated**, not claimed (§6, §10):
deploy the same release in a second environment, restore a representative database and media set,
and record time, cost and manual steps, with no application-source changes.

- [The rehearsal](#the-rehearsal-make-portability): what runs and what it proves
- [Limitations](#limitations): what a laptop rehearsal does not prove
- [Provider-specific bindings](#provider-specific-bindings): everything a new provider must supply
- [DNS and CDN cutover](#dns-and-cdn-cutover): moving live traffic
- Run reports: [docs/portability/runs/](portability/runs/)

## The rehearsal: `make portability`

```bash
make portability            # FROM=local TO=local-b; LOCAL_GIT=1 to test uncommitted changes
make portability-down       # delete the local-b cluster and its external S3
```

Both environments are local, and they differ where providers differ:

| | `local` (source) | `local-b` (target) |
| --- | --- | --- |
| Cluster | k3d `relay` on the `k3d-relay` Docker network | k3d `relay-b` on its own `relay-b` network, with its own registry |
| DNS suffix | `*.relay.localtest.me` | `*.relay-b.localtest.me` |
| TLS | local CA in `$RELAY_HOME/ca` | a different CA in `$RELAY_HOME/local-b/ca` |
| Storage class | k3s `local-path` (default class, reclaim `Delete`) | `relay-b-retain` (named explicitly, reclaim `Retain`) |
| S3 | SeaweedFS in the cluster, plain HTTP on the cluster network | SeaweedFS **outside** the cluster (`scripts/external-s3.sh`), HTTPS with its own CA, reached as `s3.relay-b.internal:8443`, like a managed S3 |
| S3 credentials | generated by `scripts/secrets.sh` | generated with the endpoint; the cluster only receives them |
| PostgreSQL bootstrap | `initdb` | `bootstrap.recovery` from the source's backups |
| Secrets backend | ESO Kubernetes provider over `relay-secret-source` | same mechanism, different values (carried ones plus its own) |

The Docker Desktop VM (about 8 GB) fits one platform at a time, so the clusters run **one after the
other**: restore stops the source cluster before it creates the target.

### Steps

`scripts/portability/run.sh` runs these; each can also run alone (`FROM`, `TO`, `RUN_ID`).

| Script | What it does |
| --- | --- |
| `external-s3.sh up` | Provisions the target's storage: CA, server certificate, per-consumer credentials, the four private buckets. For a real provider this is the provider's bucket and IAM setup, done out of band |
| `seed.sh` | The Phase 0 dataset in the source: 64 × 16 MiB random media objects (1 GiB) under immutable keys in `relay-media`, feed snapshots in `relay-feeds`, and 10,000 rows in `relay.portability.episodes`, each referencing a media object by key and SHA-256 |
| `export.sh` | Takes an on-demand CNPG backup of `relay` and `keycloak-db`: **this is the recovery point**. It then writes an `after-backup` marker and switches WAL, inventories every object to copy with its SHA-256 (read back from S3), and checks that the recovery point's base backups and end-of-backup WAL are in the inventory. It copies exactly the inventoried objects to the target with rclone, running in a Job inside the source cluster. It encrypts the secrets that must travel with the data to an age bundle, and publishes the manifest, inventories and bundle to `s3://relay-backups/portability/<run>/` on the target |
| `restore.sh` | Using only the target's storage and the age identity: fetches and checks the manifest, stops the source cluster, and bootstraps the target through GitOps (`scripts/up.sh`). The carried secrets are imported before Argo CD syncs, and `relay-root` carries each cluster's recovery target (`backupID` + `targetImmediate`) as run-time Kustomize patches, so a run needs no commit. It then waits for `bootstrap.recovery` and re-hashes every copied object on the target |
| `verify.sh` | `scripts/smoke.sh` against the target (GitOps, ESO, TLS, Gateway, S3 access rules, WAL archiving to the target's own path, Keycloak logins **with the restored users and TOTP secret**, an Argo Workflows run). It checks the restored `episodes` digest against the source's, checks the markers (`seeded` present, `after-backup` absent: recovery stopped exactly at the backup), confirms every media object the restored DB references is on the target with its SHA-256, and runs the P0-06 S3 conformance suite against the target's endpoint |
| `report.sh` | Renders the evidence in `$RELAY_HOME/portability/runs/<run>/` to `docs/portability/runs/<run>.md`: timings per step, bytes, manual steps, source changes, recovery point |

From P1-20, `verify.sh` also covers the application flows the pitch lists: login, upload, process,
publish, play and export.

### Consistency model

- **Database:** a CNPG base backup plus WAL, recovered to the end of that backup. Bucket
  synchronization is never relied on for database consistency. The restored target archives to its
  own path (`cnpg-local-b/`), never into the copied origin archive.
- **Objects:** masters and delivery files are immutable, and replacement is a new version (architecture
  rule 5). Every object that exists after the backup is a superset of what the recovery point
  references. The copy is taken from an explicit inventory, not a live listing, and each object is
  checked by SHA-256 on both sides.
- **Secrets and key material:** the Keycloak admin credentials, the test users (including the TOTP
  secret) and both database owners' credentials travel in an age-encrypted bundle
  (`s3://relay-backups/portability/<run>/secrets.age`). The age identity (`$RELAY_HOME/portability/age.key`)
  is kept apart from the target's storage. Keycloak's realm signing keys are in its database and travel
  with it. Environment-bound secrets (S3 credentials, TLS CA, registry pull secret) are **not** carried:
  the target has its own.
- **Not copied:** `relay-logs` (logs stay with the environment that wrote them), Argo CD state (rebuilt
  from git), and anything in the source cluster that is not in git, S3 or the bundle.

## Limitations

This is a **local restore rehearsal**. The run reports and the P0-08 gate must say so.

- **Not independent storage.** Both S3 endpoints are SeaweedFS 4.47. The external endpoint exercises a
  different address, TLS with a private CA, and a different credential set, not a different S3
  implementation. Before claiming storage interoperability, run `make conformance-s3` against a
  different implementation (`conformance/s3/README.md`, "Running against a managed S3").
- **Not separate failure domains.** Both clusters ran on one laptop and one Docker VM, one after the
  other. Transfer rates are Docker-bridge rates, not internet egress.
- **Same provisioner.** `relay-b-retain` and `local-path` use the same provisioner: the difference is
  the class name and reclaim policy, which the overlay must set. A provider's CSI driver (snapshot
  support, zones, IOPS classes) is not exercised.
- **Same secrets mechanism.** Both environments use the ESO Kubernetes provider. A provider overlay
  swaps the `ClusterSecretStore` for its KMS-backed secret manager. The `ExternalSecret`s do not change,
  but that backend is not exercised here.
- **Reachability is simulated.** The source reaches the target's endpoint because
  `external-s3.sh attach` joins the container to the source's Docker network. A managed S3 is reachable
  over the internet, with egress charges.
- **No application yet.** Phase 0 moves the platform and a synthetic dataset. "Zero application-source
  changes" is true by construction until P1 deploys applications. P3-08 revalidates it with the real apps.
- **Different domains.** The rehearsal moves to a new DNS suffix on purpose, to prove that nothing in
  the platform hardcodes the old one. A real migration keeps the network's media and feed domains and
  moves them with the cutover below.

Before claiming **provider** portability, run the same scripts between `provider-a` and `provider-b`
with real clusters and storage. Each needs an `env.sh` and real overlay values; the scripts do not change.

## Provider-specific bindings

Everything below differs by provider. It lives in `envs/<env>/kustomization.yaml` (manifests),
`envs/<env>/env.sh` (script settings), or the provider's own tooling. The knob-by-knob table is in
[envs/README.md](../envs/README.md).

| Binding | Where | What a provider supplies | Replacement cost |
| --- | --- | --- | --- |
| **KMS / secrets backend** | `ClusterSecretStore/relay-secrets` `.spec.provider` | The provider's secret manager (KMS-encrypted) or a Vault-API endpoint, and the workload identity ESO uses to read it | One overlay patch plus loading the values; `ExternalSecret`s unchanged |
| **Carried key material** | age bundle (`export.sh`) | Where the age identity is kept during a migration (a password manager or an HSM-backed store, separate from both providers) | Operational procedure only |
| **Storage class** | `Cluster.spec.storage.storageClass` (CNPG) | The provider's block storage class (encryption at rest, IOPS tier, zone topology, `Retain` for databases) | One overlay patch |
| **Object storage** | `ObjectStore.spec.configuration` (`endpointURL`, `endpointCA`), `argo-workflows` `artifactRepository.s3`, `env.sh` `S3_*` | Managed S3 endpoint, buckets (created out of band, private, versioning or object lock if wanted), per-consumer IAM credentials, a CA bundle if private | Overlay patches plus bucket/IAM setup; conformance-run it first (P0-06) |
| **Egress** | not in manifests | The provider's egress pricing and limits for the migration copy and for media delivery (the CDN pulls from origin) | Cost-model input (P0-08); bytes per run are in the reports |
| **Identity (workload)** | `ClusterSecretStore` auth, S3 credentials | How pods authenticate to the provider (static keys today; IRSA/workload identity later) | Overlay patch; static keys work everywhere |
| **Identity (users)** | Keycloak DB (restored), `KC_HOSTNAME` | Nothing provider-specific: realms, users and signing keys travel with the database. Only the hostname changes | One overlay patch |
| **Load balancer** | `EnvoyProxy/relay-proxy` `envoyService` | LB annotations or `loadBalancerClass`, static IP reservation | One overlay patch |
| **TLS issuer** | `ClusterIssuer/relay-issuer` | ACME with a DNS-01 solver for the DNS provider (wildcards need DNS-01) | One overlay patch plus DNS API credentials in the secret backend |
| **DNS** | outside the cluster | Records for the Gateway's address; ExternalDNS or manual | See cutover |
| **Cluster itself** | `K3D_CONFIG` in `env.sh` for local envs | A managed Kubernetes cluster (version-matched to `KUBERNETES_VERSION` in `scripts/validate.sh`) | Provider tooling, outside this repo for now |

## DNS and CDN cutover

The network's public names are the only thing listeners and podcast apps see, so they stay under the
network's control (a DNS zone the network owns, never a provider-assigned hostname):

| Name | Serves | Owner |
| --- | --- | --- |
| `media.<network domain>` | Enclosure URLs (versioned, immutable paths) | Network DNS → CDN → origin |
| `feeds.<network domain>` | RSS snapshots | Network DNS → CDN → origin |
| `www.`, `auth.`, `admin.` | Site, Keycloak, admin | Network DNS → Gateway |

Because enclosure URLs are versioned and immutable, and feeds are rendered snapshots in object storage
(architecture rule 2), media and feeds keep working from the CDN's cache and the old origin while the
new origin fills up. That is what makes the cutover low-risk.

1. **T−48 h: lower TTLs.** Lower the TTL of every record above to 60 s. Wait at least one old TTL.
2. **Prepare the target.** Run `export.sh` then `restore.sh` into the new environment (a rehearsal run
   first). The target's Gateway gets its certificates for the network domains through DNS-01, which
   does not need traffic.
3. **Add the target as a CDN origin** for `media.` and `feeds.` (secondary / failover origin), with the
   same host header and path layout. Check a sample of enclosure URLs and every feed through the new
   origin directly (`curl --resolve`), including `Range` requests.
4. **Freeze writes.** Put the admin into read-only mode, stop the publishing scheduler, and let the job
   queue drain. Public reads continue.
5. **Final delta.** Run `export.sh` again: new backup (the final recovery point), incremental object
   copy (rclone skips objects already present; they are immutable), new bundle. Restore the databases
   from that point (`restore.sh` with the new run).
6. **Verify** with `verify.sh` against the target, then log in, publish a test episode to a private feed,
   and play it.
7. **Switch.** Make the target the CDN's primary origin for `media.` and `feeds.`, then change the DNS
   records for `www.`, `auth.` and `admin.` to the target's Gateway. Purge feed paths from the CDN (media
   paths are immutable and need no purge).
8. **Unfreeze** writes on the target. Keep the source read-only and reachable for the rollback window
   (at least one feed poll interval of the slowest major app, about 24 h).
9. **Rollback** within the window: switch the CDN origin and DNS back. Anything published on the target
   during the window must be re-exported the other way, so keep that window's publishing minimal.
10. **Decommission** the source after the window: final backup to storage outside both providers, then
    delete. Raise TTLs again.

Podcast apps and directories never see the migration: feed URLs, enclosure URLs and episode GUIDs do not
change (architecture rule 4). If a feed URL itself must ever move, that is a separate procedure (HTTP 301
plus `<itunes:new-feed-url>`), handled by P1-16.
